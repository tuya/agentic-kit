01先区分三方职责

BLE 连接由 App 发起；绑定授权依赖设备与云端共享的根密钥。App 参与握手、持有会话所需材料，并在设备与云端之间转发证明和凭据。

设备 · Peripheral
广播、提供 GATT 服务，保管 auth_key，校验云端授权，保存绑定凭据并执行业务。
App · Central
扫描并连接设备，协商传输、订阅 Notify、发起协议请求，转发云端授权与设备证明。
云端 · 授权方
保管 auth_key，验证设备身份与一次性随机数，签发绑定凭据及 verify_key。

根密钥不经过 App。auth_key 只保存在设备与云端。App 首次绑定取得的是 authValue 与 serverRandom，并不取得 auth_key。

02BLE 发现、通道与分包

连接前：App 如何发现并认出设备

首次绑定与已绑定重连都先经过 BLE 扫描：设备发送广播，App 接收广播及扫描响应，识别候选设备后再发起连接。重连图中的“建立连接”之前，也需要这个发现阶段。

  1. 扫描并识别涂鸦 V6 广播。

    广播的 Service Data（AD type 0x16）使用服务 UUID 0xFD50。其中两字节、大端序的 Frame Control 包含版本位（bit 12–15，V6 为 6）、Bound Flag（bit 11，0 未绑定、1 已绑定）以及 ID Include（bit 8，指示是否携带 ID）。App 据此判断协议与绑定状态；不能假定每个广播包都有 ID。

  2. 读取发现阶段的身份线索。

    用于发现的广播若携带该 ID 字段，未绑定时为明文 PID / ProductKey，表示产品而非唯一设备；已绑定时为 HMAC-SHA-256(secret_key, device_uuid) 按协议 ID 长度取值。这里的 device_uuid 使用原始十六进制数据，不能套用旧版协议的 ASCII、PKCS7 或 AES 处理方式。

  3. 结合扫描响应与绑定记录匹配候选设备。

    扫描响应的 Manufacturer Data（AD type 0xFF，Company ID 0x07D0）还包含通信能力、security_mode 及 Flag + ID。ID Flag = 0 时，ID 是经公开 SHA-256 / XOR 规则混淆的 16 字节 device_uuid；ID Flag = 1 时，是明文的涂鸦分配 MAC。此身份字段中的 MAC 不应直接当成当前 BLE 连接地址。App 可结合这些标识与已有绑定记录识别设备；若广播带已绑定 ID，可用记录中的 secret_key 与 device_uuid 计算 HMAC 并按协议 ID 长度比对。这是一种根据字段定义推导的 App 侧匹配方法，原文没有规定唯一的 App 搜索算法。

  4. 连接后再认证。

    找到候选设备后，App 建立 BLE 连接、准备 Notify 通道，再执行 0x1000 握手与 0x1001 加密请求 / 应答。广播中的安全模式只用于提示，实际模式由设备固件决定。

发现不等于认证。广播与扫描响应帮助 App 找到候选设备。UUID 的公开混淆不提供身份认证，已绑定 ID 的 HMAC 比对也不是“解密广播”；真正进入安全会话仍需连接后的加密校验。

连接后的 GATT 通道

服务 UUID 为 0xFD50。请求与响应使用不同特征，App 在协议交互前订阅设备的 Notify。

表 1 · App 与设备的 GATT 传输方向
方向GATT 操作特征 UUID
App → 设备Write Without Response00000001-0000-1001-8001-00805F9B07D0
设备 → AppNotify00000002-0000-1001-8001-00805F9B07D0

默认 ATT MTU 为 23 字节，单次特征值最多为 20 字节（ATT MTU − 3）。协议头等开销还会占用空间，因此 20 字节不能全部当作业务数据；较大的消息需要分包与重组。

握手中的 dataMTU 是另一个具名协议字段，不应直接等同于 ATT MTU。Write Without Response 描述 GATT 写入方式，协议仍可通过 Notify 返回响应。

03两条交互路径

先看是否已绑定，以及 App 是否持有对应的 login_key 与 secret_key。这些前提决定进入首次绑定，还是直接重建安全会话。

交互路径
安全模式

选择器仅辅助阅读，不改变设备模式。图中保留全部模式的密钥标注；打印包含两条完整流程。

以下同时列出首次绑定与已绑定重连。密钥标注按模式区分，详见表 2。

首次绑定

UNBOUND → BOUND

从发现未绑定设备开始；云端验证设备证明后，签发本次绑定使用的凭据。

  1. 发现与授权。

    App 从广播发现设备，向云端取得 authValue 与 serverRandom，随后建立 BLE 连接、处理 MTU 并订阅 Notify。

  2. 0x1000 明文握手。

    交换 Flags、dataMTU、mRandom / sRandom 等材料；Mode 1/2 还交换 P-256 临时公钥。双方通过 HKDF-SHA256 派生临时密钥：Mode 0 用 key21，Mode 1/2 用 key22。

  3. 0x1001 加密查询与设备证明。

    设备返回版本、能力、绑定状态等信息，以及 RegisterKey = HMAC-SHA256_auth_key(serverRandom)。App 把 RegisterKey 与 sRandom 转交云端。

  4. 云端验证并签发凭据。

    云端验证一次性的 serverRandom 与 RegisterKey，签发 device_id、login_key、secret_key、可选凭据及 verify_key；签名覆盖本次 sRandom 和全部云端下发字段。

  5. 0x1002 提交并保存绑定。

    App 仍用临时密钥 key21 / key22 转发请求。设备使用 auth_key 校验 verify_key，验证范围包括 sRandom 及全部云端下发字段；成功后保存凭据、设置已绑定状态，并派生会话密钥。

  6. 成功响应即完成密钥切换。

    0x1002 的成功响应已经使用 key24（Mode 0）或 key25（Mode 1/2）；之后业务沿用该会话密钥。配对状态值为 0 成功、1 失败、2 已绑定；此处的切换描述仅指成功响应。

原文：V6 配对指令 · 6.4 交互流程

已绑定重连

BOUND → NEW SESSION

前提：设备已绑定，App 已持有对应的 login_key 与 secret_key。在这些前提下，无需首次绑定的云端往返，也不执行 0x1002。

  1. 扫描并匹配候选设备。

    App 从设备广播与扫描响应取得发现信息，结合已有绑定记录识别候选设备。具体字段与匹配说明见连接前的设备识别；扫描匹配尚未完成身份认证。

  2. 建立连接并交换新材料。

    App 建立 BLE 连接、准备 Notify 通道，以 0x1000 交换新的 mRandom 与 sRandom。Mode 2 还执行新的 P-256 ECDH；Mode 0/1 不执行 ECDH。

  3. 派生本次会话密钥。

    Mode 0/1 使用 key24，Mode 2 使用 key25。它们来自本次握手；重连不直接复用上一次连接的会话密钥。

  4. 0x1001 加密请求与应答完成双向认证。

    设备验证 App 的加密查询，App 验证设备的加密应答，证明双方持有正确凭据。重连时 RegisterKey = 0。

  5. 直接恢复业务。

    继续使用本次会话密钥交换业务消息。此流程没有 0x1002，也没有首次绑定的云端往返。

原文：已绑定重连

05认证成立与接收校验的边界

  • 明文仅限握手。只有 Key_type = 0 的 0x1000 允许明文；建立 BLE 连接或完成明文握手，还不代表对端已经通过认证。
  • 首个加密包验证后才进入认证状态。必须成功解密并通过 MIC 校验，才能确认对端持有正确密钥。
  • 两个方向独立维护 SeqNum。接收端严格校验序号以拒绝重放；只有通过解密与 MIC 验证的加密包才能推进接收序号，明文握手不推进接收序号。
  • 云端字段必须完整验证。设备校验的 verify_key 应覆盖本次 sRandom 和全部云端下发字段，避免 App 修改凭据或重放旧绑定数据。
  • 校验失败应终止连接。长度、密钥类型、状态、安全模式、MIC 与序号等必须校验；原文 6.5 要求任一校验失败即丢弃并断开。失败后不得自动切换到较低安全模式。

原文：6.5 接收校验与异常处理

06业务功能层：认证完成之后做什么

认证只解决“这条通道可信”。V6 原文没有另起一套业务：认证之后沿用同一份文档里逐版本累积下来的功能码与数据格式，包括 DP 控制、查询与上报，OTA，时间与天气，语音，透传与配件通道。本节把这套功能码按域拆开，说明谁发起、谁应答，以及发之前必须先满足什么。

功能码怎么分段

四位数功能码粗略划分了“认证层 / 业务层请求 / 业务层上行”，但段位只表示大致归属，方向必须逐条看。

表 3 · 功能码段位与方向
段位归属典型功能码方向
0x1000–0x1002V6 认证层握手 / 加密查询 / 配对App 发起
0x00xx业务层请求0x0027 DP 下发、0x0021 发送配网信息、0x001C 发送 SSIDApp → 设备
0x80xx业务层上行0x8006 DP 上报、0x801D 连接状态上报设备 → App

0x80xx 不等于“一定是设备上行”。透传通道里 0x801B 是下行、0x801C 是上行，两者同处 0x80xx 段而方向相反——只按段位推断方向，在透传上会直接走错。

功能码之间没有算术关系：带数据源的下发 / 上报是 0x0028 / 0x8008，查询是 0x0029，带数据源加时间戳的只有上报 0x8009。靠“下发码加固定偏移”推断上行码，推不出来。0x0000 / 0x0001 虽然也在 0x00xx 段，但原文标注它们属于 ≤PV5 的旧配对流程，见本节末尾。

先读设备信息：能力位决定后面能做什么

0x0000 的响应在 V4.x 期间不断追加字段。这些不是背景说明，而是后续哪些功能可用的开关：没读 combosflag 就开 Combo 通道，设备不会理你；不知道 packetMaxSize 就切分包，长包会被截断。

同一份命令索引里还保留更早一代的 DP 功能码：0x0002 dp 点数据下发、0x8001 dp 点数据上报、0x8003 带时间戳上报、0x8004 带标志上报、0x8005 带标志与时间戳上报（原文未给这五条标 PV）。表 5 列的是现行一族，实现时以产品对接的协议版本为准。

0x8006 与 0x8007 后续又增加了“是否需要响应帧”标志：该位为 0 时设备发完即止，App 还在等 ACK 就会一直等到超时。这是上报路径上最容易误判成“设备没响应”的一处。

广播里也能携带 DP（原文“重定义广播数据格式，可发送 dp 点数据”）。但这只适合面板显示一类的即时刷新，不能当成可靠上报通道：广播本身没有重传。

协议只搬运 DP，不定义 DP。id、类型与取值由产品物模型决定，同一个功能码在不同产品里承载的是完全不同的点。

配网：四条路径，两套流程

共用前置：帧外壳与密钥阶梯（v4.4，SDK 代码核验）

下面两条流程到字节级的细节，出自本仓库 modules/tuya-ble（v4.4 系列）源码。每个命令都装在同一种外壳里：GATT 包 = [加密模式:1B][IV:16B][AES-128-CBC 密文]（明文时为 [0x00][帧]）；帧 = [SN:4B][ack_sn:4B][cmd:2B][len:2B][载荷][CRC16:2B]。CRC16-Modbus 覆盖头与载荷；SN 严格递增、必须大于上一条收到的（防重放），ack_sn 回填对方最近一帧的 SN（隐式确认）。

流程 A · BLE 单模：配对即配网，没有「联网」这一段

  1. 广播与发现。

    广播与扫描响应的 V6 视角见第 02 节。v4.4 侧的差别在身份字段：未绑定时广播携带 product_key（产品标识，16 字节）；已绑定为 AES-ECB(MD5(secret_key), ble_id 前八字节的 hex 文本)——只有持有 secret_key 的那个 App 能认出这台设备。扫描响应另有 comm_ability 与 flag 字节（bit7 已绑定 / bit5 支持 Wi-Fi 列表扫描）。

  2. GATT 连接。

    App 连接、订阅 Notify；包长先按默认 20 字节，真正的协商在第 3 步的请求里完成。

  3. 0x0000 查询设备信息（App → 设备，KEY_11）。

    请求载荷只有 [peer_pkt_len:2B]——App 能收的最大包长；这一帧的 IV 被设备留作 server_rand，KEY_11 就是从它派生的。设备一收到就重置会话状态、换新 pair_rand——所以每次连接都要重走第 3、4 步。响应布局见表 10；发出成功即 handshake_ready。（V6 对应 0x1000 + 0x1001，见第 03 节。）

  4. 0x0001 配对请求（App → 设备，KEY_12）。

    载荷 [ble_id:16B]——App 回显设备 UUID，证明读过它的设备信息；门槛是握手已完成、尚未认证。设备比对一致即 paired = authenticated = true。响应 [result:1B]：0 成功、1 失败、2 成功且设备已绑定（老主人重连）。（V6 对应 0x1002。）

  5. 0x001E 上报联网状态（设备 → App，紧随配对成功）。

    载荷 [0x00]。单模设备的联网状态恒为 0——它没有 Wi-Fi 可连。

  6. 云端绑定与激活（BLE 之外）。

    App 走自己的移动网络向云端注册「设备 ↔ 账号」；单模设备自身没有云连接，云端数据经 App 中转。V6 索引里为把激活结果交回设备准备了 0x001B 发送设备激活信息（分包），字段布局未取得。本仓库 SDK 提供两条路（ADR 0001）：一，设备已由 IoT 客户端激活，local_key / secret_key（各 16 字节）已在设备上，BLE 控制直接借它们派生 KEY_14 / KEY_15；二，会话内激活信息回传——SDK 已实现 0x001B 的受理、校验、ACK 与绑定切换（载荷布局应用自定义，经 activation_info 回调解析），以及 0x0005 / 0x0006 解绑与复位。

  7. 业务全走 BLE（KEY_15；门槛：已绑定 + 握手完成 + 已配对 + 已认证）。

    四条 DP 命令的载荷与应答见表 11。DP 单元为 [id:1B][类型:1B][长度:2B 大端][值]，类型 raw / bool / value（有符号 32 位）/ string（UTF-8、无 NUL）/ enum / bitmap（1、2 或 4 字节）。上报 SN 每次成功后递增持久化；TLV 预算受「密文按 16 字节对齐后仍装进单包」约束（帧 14 字节开销 + 前缀，见「分包预算」）。

流程 B · BLE + Wi-Fi 双模：BLE 只负责把设备送上网

  1. 第 1–5 步与流程 A 完全相同。

    广播、连接、0x0000、0x0001、配对后的 0x001E 全部原样再走一遍；配对用的也是同一套 KEY_12 会话。差异只在能力位：comm_ability、广播 flag 的 bit5、设备信息尾部的 combosflag 告诉 App——这是双模，且支持设备侧扫描。

  2. （可选）Wi-Fi 列表扫描：0x801E / 0x801F（KEY_12）。

    App → 设备 0x801E 子命令 0x0003 请求扫描；设备侧扫描后经 0x801F 回 JSON：最多 20 个 AP、约 974 字节上限，超单包自动分包。App 按信号强度排序供用户挑 SSID。门槛与凭据下发相同：未绑定 + KEY_12 + 已配对。

  3. 凭据下发——两条实现路径。

    路径一（本仓库 SDK 实现，透传通道）：App → 设备 0x801B，载荷 [flag:2B=0x0000][subcmd:2B=0x0001][JSON {"ssid","pwd","token"}]——JSON 不得含 NUL、小于 512 字节，ssid 与 token 非空。设备校验后经 0x801C 回 5 字节 ack：[flag 回显:2B][subcmd 回显:2B][状态:1B=0]。ack 发出且发送队列排空后，凭据经回调交给应用层联网；凭据未确认前，新的 0x801B 一律丢弃不覆盖。路径二（V6 专用命令，本仓库未实现）：0x001A 查询 Combo WIFI 设备信息 → 0x001C 发送 SSID → 0x0021 发送配网信息；三条只有索引名，字段布局未取得。

  4. 设备联网并逐级报状态。

    设备连 AP、拿 DHCP。过程用 0x0022 上报配网状态（流程级：配网这一步做完没有），0x001E 再报联网状态（网络级：到底连上没有）——区别于配对后那次全 0 上报（流程 A 第 5 步）。

  5. 激活走 Wi-Fi（BLE 之外）。

    设备起 IoT 客户端：连云、用第 3 步的 token 激活，拿到 local_key / secret_key 并持久化——设备从此「已绑定」。App 侧同样可用 0x001B 把激活信息经 BLE 补交设备（索引有名）；多协议设备另有 0x0026 查询配网状态。

  6. 业务迁 Wi-Fi，BLE 退居近场。

    日常 DP 走 Wi-Fi / MQTT；手机在旁边时可近场直控——此时是「已绑定」会话：握手与会话密钥换用 KEY_14 / KEY_15（从 local_key / secret_key 派生），配对响应回 result=2，之后的 0x0027 / 0x8006 与流程 A 第 7 步是同一套字节格式。本仓库 tuya-ble 模块的「已激活设备本地控制」走的正是这条路。

分岔与汇合。配对成功处（0x0001 / 0x1002 的 result=0）分岔：单模直接进业务；双模多出「送凭据 → 联网 → 报状态 → Wi-Fi 激活」四步。之后两条路在「已绑定的 BLE 会话」上又汇合——同一套 DP 命令、同一把 KEY_15。

职责切分：0x1002 写的是云端签发的绑定凭据，解决「这台设备归谁」；0x0021 送的是设备上网需要的信息，解决「设备怎么连上网络」。两者都在 BLE 上发生，但一个属于认证层、一个属于配网层，不能互相替代。

分包预算：三个长度不是一回事

长包发送失败，通常是三个长度被当成了一个：

  1. ATT MTU。

    默认 23 字节，扣除 3 字节 ATT 头后单次最多 20 字节。这是链路层的事实，协议改不了。

  2. packetMaxSize。

    0x0000 响应里的应用层分包上限，随 MTU 交换与设备能力变化。它描述的是“一个协议包能有多大”，不是“一次 GATT 写入能有多长”。

  3. MTU 交换机制。

    连接后向设备发起的显式协商。不做这一步，就只能按默认 23 字节走。

可用的顺序是：连接 → MTU 交换 → 读 0x0000 拿能力位与 packetMaxSize → 按协议包切分，每个协议包再拆成不超过单次写入长度的片段。两个上限取小，任何一个被忽略，长包都会在某一层被截断（这一条是据字段定义推导的操作顺序，原文未给出唯一实现）。

认证层与业务层之间的三条边界

  • 不要混用旧版流程。≤V5 的 0x0000 获取信息与 0x0001 配对属于另一套安全流程；V6 的握手、查询、配对分别为 0x1000、0x1001、0x1002。功能码还在用，流程已经不是原来那条。
  • 0x1002 只写凭据。它用于写入云端签发的绑定凭据，不能理解成一个独立的“SSID / 密码下发”命令；本页也不扩展推断 Wi-Fi 配网的载荷字段。
  • 强制 LINK 层加密为真时，明文阶段没有业务。能力位说“设备要求加密”，Flag2.bit0 说“当前是否已加密”，两者都为真之后，业务帧才被接受。
