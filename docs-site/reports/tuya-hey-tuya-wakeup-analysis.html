背景与目标

背景：目前AI耳机已经实现同声传译等多种场景，涂鸦 app 也在发力hey tuya的应用场景。将两者能够融合就成为了非常必要的事情。

目标：在app被杀死或者后台情况下，使用耳机唤醒hey tuya然后进行语音交互

—— 一.1 背景与目标（「2.需求分析」整节为空）

总体设计三要点

原文以三条 bullet 给出，对应「拉起/保活 — 模式协商 — 音频上行」三个环节：

  • 耳机能够断连后拉起和保活 app——解决 app 被杀死/后台时的可达性；
  • app 启动后、连接状态下，通过新增命令上报唤醒 hey tuya——设备到 app 的模式协商（原文断句「app启动后在，连接状态下」带语病）；
  • 耳机将语音数据通过 BLE 上报给 app——音频上行通道。

进入路径 A：耳机未连接 app（冷路径，经 ibeacon）

  1. 【用户】触摸耳机，意图唤醒 hey tuya。
  2. 【耳机】因未连接 app，触发 ibeacon 广播，持续 3–5s。
  3. 【app】被拉起并连接上设备（依赖保活机制；实测耗时见 第 05 节——未锁屏 8s，锁屏最长约 25s）。
  4. 【耳机 → app】连接建立后，设备上报 dp(state=1)，请求进入 hey tuya 模式。
  5. 【app】收到 dp，初始化 hey tuya，并下发相同 dp(state=1) 完成双向确认。
  6. 【耳机】进入 hey tuya 模式；app 接收来自 BLE 的音频。

当耳机未连接app时，触发ibeacon广播(3-5s), 等app连接上设备之后，设备上报dp(state=1)，请求进入hey tuya模式，app收到dp，初始化hey tuya并下发相同dp,设备进入hey tuya模式。app收到来自ble音频。异常：其他触摸动作终止或者超时后再连接不进入hey tuya模式。

—— 3.1.2 AI耳机触发ibeacon（原文明确的两条异常分支：其他触摸动作终止；超时后再连接）

注意异常分支二「超时后再连接不进入 hey tuya模式」：按实测 8s 的连接时长，3-5s 的广播窗大概率在 app 连上之前就结束了——这条规则与实测数据的矛盾见 疑点 4。

进入路径 B：耳机已连接 app（热路径，无 ibeacon）

设备直接上报 dp(state=1)，app 初始化并回发相同 dp，耳机进入模式，BLE 音频开始上行——无广播、无拉起，一次握手即完成。

时序图里的另一套设计（二.2 流程设计说明）

「二.2 流程设计说明」节内嵌一幅五参与者完整时序图（用户 / AI耳机设备 / 手机系统 (iOS/Android) / 涂鸦APP / 云端），分三段，画的却是一套与上文正文不一致的流程：

  1. 首次配网与绑定配件——App 向手机系统发起系统配件绑定请求（AccessorySetupKit）→ 系统与设备配对连接（BT + Accessory BLE）→ App 标记「配件绑定状态：已绑定」。
  2. 自动化连接阶段——设备靠近/开盖（BT/BLE 广播）→ 手机系统识别配件并系统级拉起 App → App 获取配件 BLE 系统通信权限 → 建立 BLE 连接、设备上线。
  3. 语音交互流程（0x0094 控制 / 0091 传输）——用户触摸耳机（触发语音）→ 设备发 0x0094 opcode(request_start) → App 激活「Hey Tuya」语音引擎 → App 下发 0x0094 opcode(start_recording) → 循环音频切片传输：设备经协议 0091 上报语音原始数据流，App「透传音频数据到云端」→ 云端语义分析与 AI 处理 → 返回结果（TTS/指令）。

时序图还画出三条通话结束分支：A 用户主动结束（0x0094 request_stop / stop_recording）；B 云端检测超时（10min）EventSleep → stop_recording；C 链路异常 BLE 断连 → 清理会话资源。

03.2 主流程：逐步消息规格

F1 首次配置与配件绑定 图

  1. 用户打开设备面板。
  2. App 提示「配置设备使用配件能力」。图内还带着作者自己的旁注「面板怎么知道当前设备需要，配置高级能力？」——连触发条件都还没定。
  3. 用户点【是】→ App → 手机系统：发起系统配件绑定请求（AccessorySetupKit）→ 手机系统 → 设备：配对连接（BT + Accessory BLE）→ 设备 → App：绑定成功 → App 标记【配件绑定状态：已绑定】。
  4. 用户点【否】→ 跳过绑定，App 提示「可在面板入口重新配置」。

缺口：配对失败、用户中途取消、超时重试、重复绑定是否幂等、解绑与恢复出厂后的残留清理——图里都没有。

F2 自动拉起与连接 图

  1. 设备靠近/开盖，出 BT/BLE 广播。
  2. 手机系统识别配件，系统级拉起 App（不经过用户点击）。
  3. App → 手机系统：获取配件 BLE 系统通信权限。
  4. App → 设备：建立 BLE 连接，设备上线。

缺口：拉起失败的兜底 UX、用户拒绝权限、同时存在多台配件时的选择规则。

F3 冷路径进入 hey tuya 正文 3.1.2

  1. 用户触摸耳机。
  2. 因未连接 App，耳机触发 ibeacon 广播，持续 3–5s。
  3. App 被拉起并与设备建立连接（实测：未锁屏 8s，锁屏最长约 25s）。
  4. 设备 → App：上报 dp(state=1)，请求进入 hey tuya 模式。
  5. App 收到 dp，初始化 hey tuya，回发相同 dp(state=1)。
  6. 设备进入 hey tuya 模式，App 开始接收 BLE 音频。

异常（原文明确两条）：其他触摸动作终止；或超时后再连接——均不进入模式。F4 热路径 省略步骤 2–3：连接已在，设备直接上报 dp(state=1)，App 回发即进入。

F5 语音交互与拾音控制 图（二.2 时序图）

  1. 用户触摸耳机（触发语音）。
  2. 设备 → App：0x0094 opcode 0x01 request_start——「请求开始；设备收到 app 回复的 start_recording 后再启动录音并推音频流」。
  3. App 激活「Hey Tuya」语音引擎。
  4. App → 设备：0x0094 opcode 0x03 start_recording——「准备就绪，通知设备开始上传音频」。
  5. 用户说话，设备采集。
  6. 循环：设备 → App 协议 0091 上报语音原始数据流；App → 云端「透传音频数据到云端」。
  7. 云端语义分析 & AI 处理，返回处理结果（TTS / 指令）。
  8. 结束：设备 → App request_stop(0x02) → App → 设备 stop_recording(0x04)。

注意第 2 步的方向：是设备先开口请求，App 再授权开始——不是 App 命令设备录音。这个方向决定了「谁有权发起一次拾音」，也决定了 App 被杀死时设备端会怎样（它有请求发出去了、没人应）。

F6 心跳 正文+图

  1. 开始录音后，App → 设备：0x0094 opcode 0x05 heartbeat，每 3s 一次。
  2. 设备侧：3 个周期（约 9s）未收到即判超时。
  3. 超时后做什么——退出模式？丢半句？出提示音？未定义。

F7–F11 概要

  • F7 云端 VAD——耳机持续上报，不在端侧切句；云端判定语音起止。
  • F8 下行——BT 链路 + 系统音频播放器；iOS 设混音播放，与第三方音视频共存，且支持关闭混音；组件来自 IPC，可行性待调研。
  • F9 退出——7 条路径见 第 02 节汇总表；其中设备手势退出是设备先退、App 后退出并回发 dp(state=0)。
  • F10 提示音——可说话提示音 → Thinking Tone（思考中）→ Earcon（播完）→ Earcon（退出模式），共 4 个节点，原文属「建议」层面。
  • F11 上下文同步——进入面板时自动拉取当前 Session 对话历史；前提是 hey tuya 支持后台初始化。

03.6 两套握手怎么合并（推断）

最自洽的读法是把它们放在不同层级：

  • dp(state=1/0) 是模式级开关——表示「这台耳机现在处于 hey tuya 模式」，走涂鸦 DP 体系，云端与面板都可见，回显即双向确认。
  • 0x0094 是每一次拾音的控制——request_start / start_recording 这一对管的是「这一句开始录」，不是「进入模式」。
  • heartbeat 只在录音期间有意义——模式开着但没在录时，心跳没有对象。

按这个读法，时序图缺的只是最前面「先 dp 进模式、再 0x0094 开录」那一跳，正文缺的是「dp 进模式之后还要走 0x0094」。这只是一句解释的事，方案里一句都没有——于是两套设计各自成立、互相拆台。反过来，如果设计意图是「0x0094 一步到位、dp 只是兼容旧面板」，那就必须定义两者的去重规则（CheckList 里标了【重点考虑】的正是这一项）。两种读法的后续工作量差很多，必须先裁决。

疑点 4 · 实测数据 vs 目标体验，且广播窗自相矛盾

3.1.2 / 3.2.1 · 最重的一条

当耳机未连接app时，触发ibeacon广播(3-5s), 等app连接上设备之后，设备上报dp(state=1)……异常：其他触摸动作终止或者超时后再连接不进入hey tuya模式。

app未锁屏情况下，首次唤醒App率 80% ，唤醒后基本都可以连接上app,唤醒到app连接 8S
app 锁屏，首次唤醒app率80%，但是唤醒后很难连上app(20%)，或者需要很久 25s左右

未锁屏要等 8s 才连上，对「一键唤醒语音交互」已是勉强；锁屏场景 20% 连不上、连上要 25s，等于五分之一的用户按了没反应。文档把这组数据放在「调研情况」里就止步了。

更严重的是内部矛盾：广播窗只有 3-5s，而实测「唤醒到 app 连接 8S」——广播窗大概率在 app 连上之前就结束了，规则又规定「超时后再连接不进入hey tuya模式」。推演结果是：未锁屏场景可能系统性地「唤醒成功 → app 8s 后连上 → 已超时 → 不进入模式」。3-5s 与 8s 两个数字写在同一份文档里，没有任何人对齐过。

于是方案的真实结构是：ASK 当主干（iOS 18+）、ibeacon 当兜底（Android 与老 iOS）、dp/0x0094 当控制面、0091 当数据面——它不是四选一的犹豫，是四个约束下的拼接。这也解释了音频链路为什么非对称：上行用标准 HFP 的 8/16kHz 喂不饱 ASR，所以自建 BLE 数据通道（时序图的协议 0091）；下行要跟第三方媒体共存，所以走 BT A2DP + DuckOthers 混音。豆包 MFi 拆解（第 05 节）是同一形态的另一个实现，差别只在它用 iAP2 特权换来「不触发橙点」。

要澄清一个容易被误读的点：方案并没有把耳机「交给系统托管」——0x0094/0091 本身就是 app 直连管理耳机，和既有 Tuya 音频设备的做法一致。它向系统借的只有冷启动那一棒（把已死的 app 拉起来），其余全靠自建通道。所以真正的问题不是「为什么用 app 管耳机」，而是「冷启动那一棒在各平台分别由谁负责」——而这恰恰是方案唯一的空白：iOS 有 ASK 与实测数据，Android 只有一句验收注记，连 CDM 这类候选都没进入讨论。写清这条约束推导，评审时「为什么不用标准外设」这类问题不必再问一遍；不写，它就是评审桌上第一个被问倒的问题。

一个边界翻转：VAD 选型。本方案采用云端 VAD（耳机持续上报），而耳机研发线的既有路线是端侧 VAD（Silero 接入方案 2025-09 建档、端侧VAD方案与本方案同日 2026-01-07、统一 C++ 实现 2026-05 定稿后落地）。为「app 被杀死/后台、无界面参与」的场景放弃端侧断句，代价是持续上报的 BLE 带宽与功耗——该代价与 BR/EDR 文档记录的「电话翻译模式 BLE 带宽不足」风险同源，方案仅以 EventSleep(10min)/TTS 8s 等兜底关停对冲。EventSleep、stop_recording 在 173 篇中零命中，属 hey tuya 云端事件域，方案未给出来源链接。

与 dp63 协议族的边界：三个方案未处理的点

既有架构是「控制面走 DP 族（record_control dp63 / record_interrupt dp62 / buds_mode_switch dp65/66 / ai_mode dp67 / offline_record_state dp68）、数据面走 BLE 音频透传」两层；本方案的模式进出走新增 dp(state=1/0)、拾音开关与保活走 0x0094。为什么可能这样设计（基于文档事实的推断，方案本身未说明理由）：dp63 的 Type 字段是 TTT 录音/翻译业务的枚举命名空间，复用就要把 hey tuya 挂进 TTT 状态机及错误码体系；ibeacon 拉起场景 app 可能在冷启动，布尔 dp 的双向回显是最小握手；心跳放 BLE 透传层可能因后台场景下比 DP 通道更少依赖云端路由。但三个边界点无人处理：

  1. 双心跳并存——若设备同时支持既有录音模式与 hey tuya 模式，dp63 cmd=4 心跳与 0x0094 opcode=05 心跳的超时互斥关系未定义。
  2. 来电中断未复用 record_interrupt(dp62)——方案用 App 侧 stop_recording 自行处理，而既有族为来电专门建了 dp62；「Android 音频控制分析」还证明系统通话时普通录音会被强制静音帧，两者关系应对齐。
  3. 下行链路与「手机-耳机模式」约束相悖——该文档明确规定此模式「设备仅允许连接 BLE，如果连接 BT 需要耳机主动断开 BT」，与本方案「上行 BLE + 下行 BT」双链路共存给出相反答案，方案未引用也未解释。
