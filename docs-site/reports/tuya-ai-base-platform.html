01总览

AI基座是涂鸦的设备侧 AI 能力底座，由两半组成：传输与会话面——设备 / App 经 steam 推流网关建立加密连接，把音视频与事件流交给 omni 服务跑 AI 业务；模型服务面——apex 作为各类大模型调用的统一入口，负责选路、容错、限流与计费观测。本目录是云端开发部对这套平台的全部沉淀：协议规范、属性字典、网关设计、模型治理与工程化文档。

对 agentic-kit 仓库的读者：RTC/TAI 客户端（libstm.a，即 STM 客户端）连接的服务端正是这套体系——本目录的 2.x / 3.0 接入协议就是 tai_connect() 背后的另一端。

02版本演进主线

协议主线按建档时间排列；每级给出与上一版的核心差异。

推流网关 1.0

2023-11 · 任磊 · 服务 IPC 场景

起点是一台面向摄像头的推流网关：可变长包头（version / 分片 / 加密 / 签名等标志位）+ 命令包 / 图片包 / 音视频包，Attribute 结构承载扩展参数，HMAC-SHA256 用设备 localKey 签名。设备先调 /stream/allocateSteam 取服务器与鉴权信息，会话级重连带连接 ID、15 秒会话保留。EventID / BizCode / BizTag 事件模型和五类业务流程（抓图、移动侦测、视频消息、云存储）从这里定型——BizCode 概念一直沿用至今。

基座 2.0

方案 2025-04 · 成册 2026-01 · 李智骁 / 任磊

面向 AI 业务的全面重设计。动机是消除 TCP 多流队头阻塞（信令被数据阻塞）、改善弱网与心跳超时检测：UDP 接入层方案引入多流隔离、可配置重传 / 拥塞控制 / FEC，设备端统一经 steam-sdk 接入。报文分两层——TransportPacket（统一分片、加解密、签名，L3 = AES-CBC、L4 = AES-GCM，除 ClientHello 外全部 HMAC-SHA256 签名）与应用层 Packet（type 1-35：握手、鉴权、会话、媒体、Event Cmd）。连接 token 经 atop/mqtt 获取，重试按 5-10s 起逐次翻倍至 320-640s 封顶的指数退避。v2 汇总页（2025-06）是这族的目录索引。

基座 2.1

2026-01 · 任磊 · 做减法

传输层大幅简化：除视频帧、图片等特殊安全数据外其它数据都不加密，包头去掉 iv / security_level 字段、属性结构去掉 payload_type。新增 developer 客户端类型；加密密钥改由人马座 sagittarius 按设备 id 或家庭 id 下发。引入优雅下线：DelayDisconnect 信令（type=12）、连接最长 24 小时、设备侧空闲检测最长 12 小时——空闲后须重新取 token 连接而非重连。Event Cmd 扩展 ClearDataCache、ServerTimeout、UpdataContext、EventTrigger、EventSleep。

基座 2.2

2026-03 · 任磊 · 把加密加回来

在 2.1 基础上专注视频与图片加密：ClientHello 新增 SecuritySuit（sign_level L0/L1/L2、security_level L3/L4/L5、video_encrypt_range 与 image_encrypt_range 0-4 档），加密范围可选「只关键帧 1K / 4K / 关键帧全量 / 全帧全量」，适配不同性能终端；gcmWithPadding 在本版本固定为 1。2.1 与 2.2 的差异就是「要不要媒体加密」这一件事——分版而不是加开关，是为了让低端设备可以停留在 2.1。

基座 3.0

2026-09 · 任磊 · 重新分层

定位重写：steam 只维护客户端连接与 Omni gRPC 连接，按统一消息转发，不再解析 ACP / AG-UI / MCP。客户端协议分三族——TCP 3.0（DATA / PING / PONG）、WS 3.0（复用 websocket 内置机制）、STM 3.0（外层帧 + 33 字节绑定握手 + 私有 QUIC 提供一条可靠流 + 单流统一消息 ≤1MiB）。亮点是多路聚合：同一逻辑连接并发 TLS 与 DTLS 多条物理链路、客户端自行选路切换，全部断开后 60 秒内无新链路并入才关闭；无应用层心跳，反压经 QUIC 流控自然传导。同端口按首字节区分 2.x / 3.0 各协议。

开发者协议文档 V2

2026-05 · 任磊 · 面向外部的裸协议

与内部协议并行的另一条线：让外部开发者在 agentic-kit 未覆盖的语种 / 平台上不依赖 SDK 直接接入。统一二进制包头（type 0-6：system / text / audio / video / image / file / mcp）+ TLV 属性区 + QUIC varint 长度，跑在 TLS 1.2/1.3、WebSocket over TLS、DTLS 上；系统命令走 JSON（15 个 cmd），轮次语义由 FIRST/LAST + commit/finish 构成。视频与图片始终加密上传（SDK 纯透传），文件上限 50 MB，MCP 大数据用 ChunkDesc/$attach 分块。内部版的复杂机制（数据复用等）对外无收益，被刻意拿掉了。

03接入与传输

传输形态按时间叠加而非替换，每一版都新增一种接入方式：

  • TCP / TLS——1.0 起的基线，2.0 加上 UDP 方案的多流隔离与可配置重传 / 拥塞控制 / FEC（UDP 方案；信令走 0 号流，SessionNew / Event / SessionClose 的完整时序在文档内）。
  • WebSocket——Web 端接入（2025-10）：steam 监听 443，web 端经 moto 的 /v2/stream/allocateSteam（新增 clientType=web）拿 wss 地址；域名 + 证书复用 + url token 与 ClientHello 双重鉴权。
  • DTLS——UDP SDK 升级 DTLS（2025-12）：按公司安全要求把私有安全传输协议换成标准 DTLS，域名替代 IP、等级协商改造，云 / 端 / SDK 合计 17 人天。
  • WebRTC / QUIC——2.1/2.2 的两条接入支线：webrtc 接入与quic 接入两页均只有标题，正文空缺；3.0 的 STM 承载里倒是内置了自定义 QUIC（MSS 1200、有效分片 1184、FEC 关闭）。
  • 音频标准化——AI基座音频标准化（2026-07）：把音频编码转换从下游 Supersonic 上移到 steam 统一处理，上行各种编码统一转 PCM 16kHz / 单声道 / 16bit，下行按会话声明编码整场锁定——修复同一连接内下行编码混发导致的杂音 / 卡顿；按设备灰度，默认关闭。
  • 扩展协议——接入层扩展协议：2.0 之上的信令 / 流管理扩展，与 UDP 方案同批成稿。

04会话与业务语义

  • 属性字典——AI基座v2属性（修改记录 2026-01 → 2026-08，全库被引最多）：属性号段 1-999 系统 / 1000-1999 AI 业务 / 2000-2999 IPC 业务；连接属性（PingInterval 默认 60000ms、1.5 倍间隔无数据断开）、媒体参数族（70-104）、UserData 111、Signature 115，加上安全套件枚举、连接 / 会话状态码与关闭错误码（200/400/401/404/408/500/504/601-610、omni 1000-1008）。
  • bizcode 业务编码——bizcode 说明是总表：v1.0 抓图（7-10）、AI 云存储 / 录像（11-18、21）、视频消息（22-24）、宠物识别（26）、通用 AI 业务（65537）、v2.2 普通云存储与音视频转发（100/101/102）。两条硬约束：同一设备的 AI 云存储片段不可重复（联播会回退）、一次会话最多录像 5 分钟。2.0 bizcode 业务说明补充各产品差异（喂鸟器单片段、宠物检测多片段 + 抽帧 + 每 10 秒回调）。
  • IPC 业务属性——IPC 业务属性：v2.0 下走嵌套 Attributes，号段 2000-2999（StartTime / PerDuration / TotalDuration / FragFlag / ExtImage / ExtStrategy / BizIdentification）。
  • 对象存储——cetus 使用说明：各业务上传 bucket 与 objectKey 规则（airtake-temp-data-ai，autoclean/1-day/* 一天自动清理），createToken / PUT（AWS4-HMAC-SHA256）/ GET（X-Amz-Expires=3600）三件套；图片 / 录像内容均需加密，密钥来自 SessionResponse 或设备密钥。

05Apex 与模型服务

Apex 是大模型调用的统一入口，本目录近半数文档（标签 Apex×20）围绕它，且几乎全部出自王升一人（2026-04 起）。

  • 网关本体——apex 接入网关（2024-08，全库最早的一批）：按（模型, 区域）组成模型单元，评分 = 成功率×100 + 延时得分选点，令牌桶限流、多模型 code 容错、主动缓存；apollo 配置 per-provider key、group 按百分比 / 优先级分配。AI 服务 (APEX) 设计文档（2024-12）补充架构：kafka 消息服务器 + http api + worker，业务方不再自己处理音视频与模型接入。
  • 高可用——高可用与容错（2026-07）的判断很直白：选路做得好、失败后的容错几乎空白。方案 A1 调用失败重试 + 主动 failover（failover 成功率目标 ≥90%）、A2 硬熔断，辅以请求防护与可观测，全程灰度开关秒级回滚。
  • 错误码——标准错误码封装：五家上游（DashScope / Ark / Gemini / Azure OpenAI / Zenlayer）统一映射到 apex 既有 251-258 / 500，不新增不改值。两个陷阱被明确点出：内容违规多藏在 200 响应而非 error 路径；429 不等于可重试（欠费 / 额度耗尽落 258）。
  • 线上模型——apex 线上可用模型：脚本自动维护，7 区域 × 16 供应商，全区去重 119 个模型（多模态对话 87、生图 16、视频生成 6、实时语音 5、纯文本 4、快速决策 1）。模型下线信息同步治理退役：gpt-5-chat、gemini-2.0-flash 等已下线，豆包系 8 模型 2026-09-21 统一退场换 seed-2.0-lite/mini，gpt-4o 排到 2027-04。
  • response-api——接口文档：封装 OpenAI Responses 有状态会话——首轮不传句柄、响应句柄保存后续携带并照传全量 messages，网关只下发增量；句柄绑定凭证通道并记录内容指纹，指纹不符等 13 种情况自动回落全量重放，调用方无感。可用模型：PRO 14 个（仅 gpt-6-luna / gpt-6-sol / gpt-6.1-sol 七区全开）。
  • decision-api——接入说明（2026-10）：输入 evidence + questions，一次调用返回类型化答案（choice / predicate / score / refusal）+ 置信度 + 候选概率分布，不做自由文本生成，面向工单路由、内容分类、规则判定。可用模型均处预发（StartLux、阿里决策、Jev）。
  • 治理与演进——技术优化规划：重写模型评分（旧 leader 集中式评分的七缺陷：分母污染致限流振荡、空闲回血、窗口口径差 40 倍……）、channel 级切流（有效权重 = 配置权重 × h × g，急停 + 缓调）、清理 IPC 弃用代码约 16500 行。bifrost 迁移分析（2026-11-05，快照最新一篇）：apex 已验证能力按 U1-U13 迁移单元逐个判定迁 / 不迁，bifrost 承接新增文本域流量、apex 继续服务存量与多模态。

06AIGC 与实时语音

  • 生图——生图 API 扩展字段：ext_json 不为空即走新模式，原字段全部忽略，按豆包 / Gemini / 阿里三套厂商 schema 透传；图生图最多 14 张（URL 或 Base64）。文生图图片编辑接口统一化（2025-08，草稿）调研了五家接口的异同（千问异步、Google 走项目证书），统一化设计尚未成稿。
  • 视频生成——Apex 视频生成 API：TyaiVideoCreateTask 提交即回 task_id、TyaiVideoQueryTask 查询，适用 seedance-2-0；媒体只收公网 URL，时长 4-15 秒，产物为火山临时链接 24 小时有效。查询时 model_codes 必传且须与创建时一致，否则路由不到对应 API Key。配套测试记录页只留了两个 task_id。
  • 实时语音——实时语音大模型 API 设计（117KB，本目录最重的接口设计）：S2S 走 gRPC 双向流 + Protobuf 3，音频 bytes 直传免 Base64；输入固定契约 PCM 16bit / 16kHz / mono（推荐 100ms / 3200 字节一包），输出透传不转码、由首个 audio_delta「格式头包」告知格式；会话最长 30 分钟、无需应用层心跳。附 Azure OpenAI / 火山豆包 / Gemini / 阿里 Qwen-Omni Realtime 四家在连接管理、计费、音色、Function Calling 上的深度对比。
  • AIGC 内容标识——内容标识方案：落实《人工智能生成合成内容标识办法》（2025-09-01 施行）与强制国标 GB 45438-2025，显式水印 + 元数据隐式标识 7 字段；豆包链路开火山原生隐式水印、阿里链路外挂 SASE 打标服务。apex 自我定位是「技术支持者」——法定义务主体是面向 C 端的终端 App。
  • 思考档位——思考等级查询 api：按 model code 查各模型直传三方的 thinking_level 映射，只读不调用；档位三形态（有值 / 仅开关 / 不支持自动收敛）。

07安全与加密

  • 图片加密——AI基座图片加密：上传临时存储的加密文件格式按安全等级分 v1（固定 L3 全量）/ v2（等级由 security_level 定，MJPEG 用）/ v3（范围由 encrypt_range 定，支持「加密段 + 明文段」拼接）/ v0xabcdef00（IPC 非 MJPEG 帧固定 L3）四个版本，整型一律小端。
  • 文件加密——AI基座文件加密（2026-10，快照期最新成稿之一）：64 字节文件头（version=4 / iv 16B / size 4B / security_level 1B 默认 4 / reserve 39B）+ 全密文数据区，L4 = AES128-GCM、L5 = AES256-GCM，均不带 padding。
  • 链路安全——协议层的等级与范围协商见 2.2 的 SecuritySuit（第 02 节）；传输面从私有安全协议到标准 DTLS 的整体迁移见DTLS 升级（第 03 节）。
  • 端侧视觉资源加密上行——标题页、需求文档与设想方案三页 2026-03-05 同日建立后均为空壳，这条线停留在标题阶段。

08成本与工程化

  • Cost Center SDK 三部曲——接入技术方案（设计稿）：各供应商凭据（apiKey/ak/sk/baseUrl）从 Apollo 明文切到公司统一 Cost Center SDK，业务方只给「业务模型名」；沿用 entryPoint「配置不可变 + 整体替换」，SDK 取不到自动回退 Apollo，30+ 处 provider 代码零改动。重构方案把范围扩成三件闭环的事：凭证来源 + 以模型 code 为中心的配置结构 + 模型重定向（请求 A 实走 B）。发布计划（2026-07）：覆盖 7 区 222 个模型定义，Apollo 开关热切换 15 秒生效，金丝雀 → 分批 → 全量，改回开关即秒级回滚。
  • 工程基建——ci-runner 部署指南：平台无共享 runner 时在 Linux 虚拟机上自建 GitLab Runner（docker executor）的幂等部署脚本，覆盖内网受限环境的离线镜像导入与故障排查。
  • HeyTuya 异步委派——HeyTuya 异步委派设备能力 v0.1（2026-10，草稿）：以「帮我给 xxx 发邮件」为首个场景，Omni 完成授权与内容确认后由主模型创建持久任务，设备侧完成后回传真实结果、Omni 续跑总结并定向下发文本 + TTS；首期用模拟邮件执行器在一款智能音箱上打通闭环，9 个工作包合计 120 小时。注意它挂在「AI基座v2汇总」页之下，是 v2 汇总的唯一子页。
